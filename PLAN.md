> Этот файл = исходный утверждённый план + раздел «что реально получилось».
> Архитектура заметно эволюционировала по ходу разработки на живом GNOME/Wayland —

## Статус реализации (Веха 1 — ядро автопереключения)

**Готово и работает:** перехват клавиатуры (пассивно), детекция неверной раскладки
(триграммы RU/EN + словари), исправление через буфер обмена, переключение раскладки,
отмена, горячие клавиши, пользовательские словари, защита команд, доверенный контекст,
защита от порчи текста, CLI, IPC, systemd-сервис, udev/install.

**Окружение:** Ubuntu 26.04, Wayland, GNOME. Код в `/home/alfer/Projects/puntu/`.
Раскладки `us`+`ru`, сочетание переключения `<Super>space`.

### Ключевые отклонения от исходного плана (и почему)

По ходу отладки на реальном GNOME/Wayland выяснилось, что несколько «подтверждённых»
допущений плана не работают. Итоговые решения:

1. **Без `EVIOCGRAB` и ре-эмита — пассивное чтение.**
   Захват клавиатуры + пере-излучение через uinput при любом изъяне **полностью ломал ввод**
   (зависший процесс держал клавиатуру). Перешли на **пассивное** чтение `/dev/input/event*`
   (evdev раздаёт события всем читателям) — мы только *читаем* и *впрыскиваем исправления*.
   Если демон падает/зависает — ввод не страдает. См. `input/capture.rs`, `input/mod.rs`.

2. **Без libxkbcommon — собственные таблицы раскладок.**
   Для фиксированной пары ЙЦУКЕН/QWERTY таблицы в `keymap.rs` точны и убирают системные
   `-dev` зависимости. xkbcommon — апгрейд для произвольных раскладок (позже).

3. **Активную раскладку читаем из `mru-sources[0]`, а не из `current`; и не переключаем сами.**
   Критично: на GNOME `gsettings … current` **не обновляется**, когда раскладку переключает
   Mutter (по `Super+Space`) — застревает на старом значении. Достоверный источник активной
   раскладки — **первый элемент `mru-sources`** (most-recently-used), его Mutter держит свежим.
   Читаем его **заново на каждом завершённом слове** (подпроцесс `gsettings`, не GIO; watcher
   убран как ненадёжный). Из-за неверного чтения `current` ранее ломалось всё: английский «не
   переводился», были ложные правки русского. Авто-переключение раскладки тоже убрано (инъекция
   `Super` открывала «Обзор» GNOME и сбивала фокус) — слова исправляются на месте, раскладку
   пользователь переключает сам. См. `layout.rs::active_lang`.

4. **Исправление — вставкой из буфера обмена, не повтором keycode.**
   Mutter **держит для нашего uinput-устройства фиксированную (us) раскладку** и не меняет её —
   повтор keycode для кириллицы давал латиницу. Поэтому целевой текст кладём в буфер
   (`wl-copy`) и вставляем `Ctrl+V` — это не зависит от раскладки. Прежнее содержимое буфера
   сохраняем и восстанавливаем. Нужен пакет **`wl-clipboard`**. См. `clipboard.rs`, `action.rs`.

5. **Защита от порчи текста (type-ahead guard).**
   Вставка задержана (~десятки мс), и при быстром наборе `backspace` стирал не те символы
   («коверкало» текст). Решение: **не исправлять, если есть необработанный ввод** (look-ahead
   по пакету событий + `poll` дескриптора). Лучше пропустить, чем испортить. Для быстрого
   набора — ручной хоткей. См. `input/capture.rs::has_pending_input`.

6. **Доверенный контекст — мягче, чем в плане.**
   Клик мышью, чтобы сфокусироваться и начать **новое** слово, больше не блокирует исправление.
   Новое слово, набранное подряд, — доверенное; защита от правки середины остаётся (буфер
   очищается при движении курсора посреди слова). См. `buffer.rs`.

7. **Модель — из встроенных словников, не из `.trigrams`.**
   Триграммы строятся при старте из `data/ru.words` (~12 000 слов) и `data/en.words` (~8 000)
   через `include_str!`. Словники — топ частотных слов из открытого списка OpenSubtitles
   (Hermit Dave / FrequencyWords) + немного техслов; чистая кириллица/латиница, длина 2–20.
   `puntu-train` — инспектор оценок, не генератор. Правило решения:
   `score_alt − score_cur > switch_delta(0.7)` **и** `score_alt ≥ alt_valid_min(−3.3)`.
   Чем больше словник — тем выше полнота без потери точности.

8. **Токенизатор: буквы на клавишах пунктуации.**
   Русские буквы `б ж э ю х ъ ё` сидят на EN-клавишах `, ; ' . [ ] \``. Клавиша считается частью
   слова, если она буква **хотя бы в одной** раскладке — иначе слова `будем`/`ужин` рвались.

9. **Зависимости фактические:** `evdev`, `libc`, `serde`/`toml`, `notify`, `clap`,
   `directories`, `signal-hook`, `tracing`, `crossbeam-channel`, `anyhow`/`thiserror`.
   `fst` используется для опционального большого словаря RU (`puntu build-dict` →
   `~/.config/puntu/russian.fst`). **Не используются:** `xkbcommon`, `gio`/`glib`.

### Известные ограничения (следствие пассивной модели на Wayland)
- Автозамена срабатывает, когда после слова есть микропауза; при сплошном быстром наборе
  слова пропускаются (защита от порчи) — на этот случай ручной хоткей `Shift+Pause`.
- Слово, завершённое Enter, в чатах успевает отправиться до исправления.
- Нужен `wl-clipboard`; вставка идёт через `Ctrl+V` (в терминалах это не «вставка» — там
  свой shortcut, поэтому терминалы лучше исключать профилем приложения в M3).
- Качество детекции ограничено размером словников `data/*.words` (расширяемо).

### Конвертация вставленного текста (`paste_convert`) — реализовано (opt-in)

**Проблема.** Демон читает клавиатуру *пассивно* и копит слово из физических keycode. Текст,
вставленный из буфера (`Ctrl+V`), **не приходит как нажатия клавиш** — его кладёт приложение
через clipboard-протокол. Поэтому буфер слова пуст (а `Ctrl+V` к тому же аккорд → `Invalidate`),
и на пробеле после вставки `buffer.finish()` возвращает `None`, цикл делает `continue` **до**
строки лога → раньше перевода не было и в логах пусто. Это следствие модели, а не баг.

**Решение — триггер «вставка + разделитель».** На `Ctrl+V` запоминаем факт вставки
(`pending_paste`). Если следующая клавиша — разделитель (пробел/таб/энтер), буфер пуст (между
вставкой и пробелом ничего не печатали), аккорд не зажат и демон не на паузе — читаем буфер через
`wl-paste`, прогоняем через `detect::convert_text` (по словам; верно набранные слова и пробелы не
трогаем) и заменяем: backspace на длину вставки + разделитель, затем вставка исправленной формы.
К моменту разделителя `Ctrl` уже отпущен (нет `Ctrl+Backspace`) и вставка успела примениться —
поэтому замена безопасна. Type-ahead guard тот же, что у обычной автозамены. Буфер пользователя
сохраняется/восстанавливается. См. `input/capture.rs::try_paste_convert`, `detect::convert_text`.

**Ограничения.** Срабатывает только на `Ctrl+V` + последующий разделитель (не на средней кнопке /
меню «Вставить»); ориентирован на однострочный текстовый ввод; нетекстовое содержимое буфера не
трогаем. Альтернатива для произвольного выделения остаётся — `Shift+Pause` (`convert_selection`).

**Переключатель `paste_convert` (по умолчанию `false`).** Файловый, hot-reload флаг в
`config.toml` — тем же приёмом, что правки словарей. Меняется **из CLI**
(`puntu config set paste_convert on`) и **из будущего GUI** через общий `Config::load`/`save_to`,
без отдельного протокола поверх сокета. Точки: `config.rs` (поле + `save_to`), `main.rs`
(`puntu config show|set`), `keymap.rs::KEY_V`, `input/{capture,mod}.rs`, `config.example.toml`.

### Обучение словаря из жестов и UI (v0.3.0) — реализовано

Двустороннее обучение поверх IBus-движка (частично закрывает M2/M3):
- **предложение после повторов**: третий ручной перевод одного слова (флип вперёд `Ctrl+`` ` ``
  или конверсия выделения) → zenity-вопрос «Запомнить?»; порог `learning.suggest_after`
  (0 = выкл), счётчик в памяти движка, слова уже известные словарям не считаются;
- **хоткей запоминания** `Ctrl+Alt+D` (`ibus_hotkeys.remember_key`, «none» = выкл):
  выделенное (или последнее набранное) слово → в распознаваемые; подсказка у курсора;
- **окно словаря** `puntu dict ui` (zenity, без новых зависимостей): пары
  «слово / как набирается», добавление/удаление; встроенные EN-аббревиатуры скрыты
  (`UserDict::user_recognized`);
- фильтр `learnable`: только одиночные чистые слова (без цифр/команд/смешанных алфавитов);
- всё подхватывается hot-reload'ом за ~секунду. Откат автозамены (обучение «не трогать»)
  работает как раньше.

### Экспорт/импорт словаря — реализовано

`puntu dict export [файл]` (без файла — в stdout) выгружает **только пользовательские** списки
в один переносимый текстовый файл; `puntu dict import <файл>` сливает его обратно. Те же
действия — кнопками «Экспорт…»/«Импорт…» во вкладке «Словарь» приложения (диалог выбора файла
через zenity в фоновом потоке, чтобы окно не подвисало).

Формат — секции `[<список> <язык>]` и слово на строку, как в самих файлах списков: файл
читается и правится руками. Встроенные словари (EN-аббревиатуры, список команд) в экспорт не
попадают — иначе при импорте на другой машине они бы «застыли» в личных списках пользователя.
Импорт идёт через `UserDict::add`, поэтому работает то же разрешение конфликтов («последнее
действие побеждает»), что и при обычном добавлении. Повторный импорт того же файла ничего не
дублирует и ничего не меняет. См. `UserDict::{export,import_str}`.

### Горячее применение config.toml — реализовано

Движок читал конфиг один раз при старте, поэтому окно настроек применяло изменения
перезапуском IBus — а он выбивает движок из всех окон на пару секунд и роняет удержанное
слово. Больнее всего это стало с секцией `[ibus_clients]`, весь смысл которой — «допиши игру
в список и работай дальше».

Настройки переехали в разделяемый слот `SettingsSlot = Arc<RwLock<Arc<EngineSettings>>>` —
тот же приём, что уже был у детектора. Движок читает его на каждое событие клавиши
(`PuntuEngine::settings`, копия `PuntuEngine::detector`), а watcher конфигурационного
каталога подменяет содержимое. Два значения, которые кэшировались при создании движка, теперь
обновляются явно: `TapDetector::max_hold` (пушится в начале `process_key_event`) и
`hold_commit` (читается из слота в `arm_hold_timer`).

Watcher (`ibus/runtime.rs::reload_watcher`) теперь классифицирует и `config.toml`. Правка
только `[detect]` пересобирает детектор **без** перечитывания `russian.fst`: watcher держит
свой экземпляр `Models` и сравнивает секции (`DetectConfig: PartialEq`). Битый TOML —
предупреждение в журнал и сохранение прежних настроек, как в `apply_reload` у uinput-демона.

Окно настроек лишилось всей машинерии отложенного авто-перезапуска (`AUTO_APPLY_DELAY`,
`apply_at`, `restart_rx`, состояния `Pending`/`Restarting`): сохранение файла и есть
применение.

### Словарь замен и сниппеты — реализовано

Файл `replacements.txt` с парами `ключ = значение`, отдельным полем в `UserDict`: это map, а не
множество слов, поэтому в `ListKind`/`LangLists` он не лезет. Разбор свой, не через `read_list`
— тот приводит всю строку к нижнему регистру, а значение обязано сохранить регистр
(`адр = ул. Пушкина, д. 1`). Делится по первому `=`, так что значение может содержать ещё.

Раскрытие — в `expand_replacement` (свободная функция, поэтому проверяется тестом без DBus и
async-рантайма), вызывается из `decide_renderings` **до** детектора. Ключ сравнивается с
**обоими** чтениями клавиш: «забыл переключить раскладку» — это ровно тот случай, для которого
существует Puntu, и таблица, работающая лишь в одной из раскладок, не помогала бы именно там.
При коллизии ключей первым пробуется чтение, которое рендерит текущий режим, — иначе результат
зависел бы от порядка хеша. Регистр — через существующий `match_case`, но только для
односложных значений; у многословных он часть текста. `fix_case` к значению не применяется.

Ограничители дались бесплатно: гарда `autocorrect && !in_terminal()` в `decide_renderings`
теперь общая для замен и детектора, так что в терминале и при `dry_run` замены молчат.

`Held.auto_converted: bool` заменён на `enum HeldSource { Typed, AutoConverted, Replacement }`
— у флипа три разных смысла, и компилятор теперь проверяет полноту. `Replacement` глушит и
обучение (откат правила, написанного пользователем, ничему не учит), и счётчик ручных
конверсий, и fallback `handle_remember`.

CLI: `puntu dict replace <ключ> <значение…>` (значение до конца строки, кавычки не нужны),
`puntu dict list --replacements`; `puntu dict rm` убирает и замену с таким ключом. Секция
`[replacements]` в экспорте/импорте, `replacements.txt` в watcher'е — подхватывается на лету.

Не сделано намеренно: вкладки в приложении (добавим после обкатки) и поддержки в uinput-демоне
— он отключён `install.sh`, второй destructive-путь ради этого не нужен.

### Разбор отчётов после 0.9.5 — исправлено (2026-09)

Четыре жалобы, три из них — про одно и то же место: удержанное в preedit слово и то, кто его
коммитит.

- **«При клике слово вставляется туда, куда кликнул».** Все preedit движок шлёт в режиме
  `IBUS_ENGINE_PREEDIT_COMMIT`, а контракт этого режима — preedit коммитит **сам IBus**, не
  движок: клиенты с `ClientCommitPreedit` (ibus-gtk3 из обработчика button-press, ibus-gtk4
  внутри `reset`, gnome-shell/mutter в `clutter_input_focus_reset` ещё до доставки клика
  приложению) делают это синхронно и по старой каретке; для остальных (плагин Qt, XIM) это
  делает демон в `_ic_reset`/`focus_out`, а при `disable` — всегда. Движок же в `reset`/
  `focus_out`/`disable`/`enable` коммитил слово **ещё раз** — уже по новой каретке, а после
  смены фокуса гонка с перепривязкой движка к новому контексту клала его в соседнее окно.
  Теперь эти четыре колбэка только забывают слово (`forget_pending`); движок коммитит сам
  лишь внутри события клавиши (аккорд, навигация, Enter/Tab, уход в прозрачность), по таймеру
  и при смене режима. Таймер `hold_commit_ms` остаётся как страховка.
- **Ctrl+стрелка: нельзя печатать и ходить стрелками, слова пропадают.** Аккорд сбрасывал
  буфер, не трогая preedit: слово, о котором движок забыл, оставалось на экране, тулкит считал
  каретку «в композиции» (стрелки не ходят), а следующая буква заменяла его целиком. Аккорд
  теперь коммитит всё набранное (`flush_all`). Заодно в `toggle_mode` исправлен порядок
  clear→commit — Chromium/Electron клипали слово при коммите с последующей очисткой preedit.
- **После принудительного перевода нельзя перевести обратно («нет нового выделения»).**
  Guard от остатка PRIMARY считал остатком и переведённый текст. Переведённый текст в PRIMARY
  может оказаться только выделением пользователя (до вставки его не существовало) — это и
  есть жест «переведи обратно». Остаток — только исходный текст, и даже он свежий, если после
  перевода был `reset` (клик) и с тех пор ничего не набрано (`selection_remade_since`).
  Клиенты, чей `SetSurroundingText` несёт настоящий anchor (`gnome-shell`, плагин Qt),
  сообщением «cursor == anchor» говорят «ничего не выделено» — тогда PRIMARY не читается
  вовсе (там только остаток). GTK-модуль IBus (любой версии GTK) и XIM anchor не несут и
  остаются на PRIMARY — см. уточнение в аудите 2026-11 ниже: имена там были записаны
  неверно. Два тапа подряд больше не запускают две конверсии одного выделения
  (`convert_busy`). `wl-paste --watch` (точная свежесть PRIMARY) на mutter не работает —
  нужен wlr-data-control.
- **Счётчик ручных переводов.** Слова, известные словарям, не считались вовсе («нечему
  учиться») — а именно их и переводят вручную чаще всего: детектор отказывается от `vs`/`ns`/
  `yt` (читаются как английские) и от всего, что попало в learned после одного отката.
  Считаются все ручные переводы; на пороге незнакомое слово → «запомнить» (как раньше),
  знакомое → «всегда переводить `typed` → `word`» (force-список набранной формы; `UserDict::add`
  снимает её с списков исключений, и наоборот — force и исключение не сосуществуют).

Вторая волна, после установки первой:

- **«Писал букву к — писалась r».** В RU-режиме исключение для латинских аббревиатур (`ui`,
  `api`) срабатывало и на одну букву: `r` есть в английском списке (SMS «are»), а «к» нет ни
  в одном русском — и увиденное в preedit «к» превращалось в `r` по пробелу. Одиночные буквы в
  RU-режиме теперь всегда русские. В режиме автозамены «и»/«у»/«а» не переводились из-за `b`,
  `e`, `f` в `learned.en.txt` — движок сам добавлял их при откате одиночной автозамены. Больше
  не добавляет, а старые однобуквенные записи learned-списков игнорирует при загрузке
  (`manual` — слова пользователя — честно учитываются).
- **«Запомнить» добавило `ghbdtn` как английское слово.** Кандидат брался из PRIMARY раньше,
  чем из только что набранного слова, а PRIMARY — это последнее выделение где угодно (своё
  окно Puntu публикует выделения полей само). Порядок теперь: выделение по данным клиента →
  удержанное слово → PRIMARY, и только если клиент не сказал «ничего не выделено». И
  семантика: если кандидат неизвестен, а его чтение в другой раскладке — словарное слово, это
  форма «не в той раскладке», и запоминать её как слово значит навсегда выключить её перевод;
  вместо этого она идёт в force-список (`remember_action`).
- **`debug_log` в config.toml.** Подробный лог без перезапуска: фильтр tracing за
  `reload::Layer`, watcher конфига переключает его. `PUNTU_LOG=… ibus restart` на GNOME не
  работал никогда: ibus-daemon — потомок gnome-shell и перезапускается с окружением сессии.

### Аудит всего проекта — исправлено (2026-11)

Проверка «найти всё, что работает неправильно». Каждый пункт воспроизведён до исправления:
движок запускался на **приватной** шине `dbus-daemon` (переменная `IBUS_ADDRESS`, сессионный
IBus не затрагивается), а скрипт играл роль ibus-daemon и текстового поля. На установленной
сборке падало 15 сценариев из 24, после исправлений — 0.

**Порядок вызовов IBus (корень нескольких «плавающих» жалоб).**

- **Вызовы обрабатывались не по порядку.** zbus по умолчанию запускает задачу на каждый
  входящий вызов, и задачи гоняются за блокировкой интерфейса. ibus-daemon шлёт
  `FocusOutId(старое)`, `FocusInId(новое)`, `SetCapabilities`… пачкой, не дожидаясь ответов,
  и в живом логе `focus_out` раз в несколько минут приходил ПОСЛЕ `focus_in` — и стирал имя
  клиента, возможности и purpose только что открытого поля (`client=""`). Отсюда: список
  `passthrough_clients` и правило «нет preedit» срабатывали через раз; два символа из одной
  пачки могли поменяться местами. Исправление — одно слово во вшитом librush:
  `#[interface(…, spawn = false)]`; тест `engine_calls_are_handled_in_the_order_they_arrive`
  не даёт его потерять при переносе патчей.
- **ContentType: свойство врало демону.** В librush у `ContentType` был геттер, всегда
  отвечавший `(0, 0)`. zbus после каждой записи шлёт `PropertiesChanged` со значением из
  геттера, а ibus-daemon держит кэш этого свойства и шлёт тип поля, только когда он
  отличается от последнего. Ложный сигнал сбрасывал кэш в `(0, 0)` — и демон больше никогда
  не говорил движку «снова обычное поле». Это и было исходное «после терминала движок
  молчит везде». Обходной путь (движок сам обнулял purpose на каждом фокусе) держался на
  порядке вызовов, которого не было: `ContentType`, обработанный раньше своего `FocusIn`,
  стирался — и поле пароля оставалось без защиты (`gfhjkm` в preedit и «пароль» по пробелу),
  а терминал — с автозаменой. Теперь свойство только на запись, как в самом IBus
  (`access='write'`): сигнала нет, кэш демона честный. Движок purpose и возможности **не
  сбрасывает никогда** — последнее присланное и есть состояние поля в фокусе. Записи свойств
  — единственное, что всё ещё может прийти не по порядку (их обрабатывает встроенный
  интерфейс zbus в отдельной задаче), поэтому из двух побеждает отправленная позже: по
  серийному номеру D-Bus (`is_stale_write`). `FocusOutId` чужого контекста игнорируется.
- **Пароли в логе.** Строка `event: keysym=…` писалась до проверки «это поле пароля?». С
  `debug_log = true` в `engine.log` лежали пароли по клавишам. В полях пароля/PIN события
  клавиш больше не логируются вовсе; файл лога создаётся с правами `0600`.

**Что считать словом.**

- **Дописанный «хвост» слова переводился как отдельное слово.** `walkes␣`, два Backspace,
  `d␣` → `walkeв`; `thw` → `thу`; `words` → `worвы`; `5th` → `5ер`. Буфер считает слово
  новым с первой буквы и не знает, что стоит перед кареткой. Именно отсюда записи `ds`, `st`,
  `el`, `fa`, `b`, `e`, `f` в `learned.en.txt`. Теперь движок ведёт учёт текста перед кареткой
  (`Tail`): что закоммитил сам, какие разделители вставило приложение, сколько съел Backspace.
  Слово, начатое сразу после буквы или цифры, — фрагмент: удерживается как набрано, без
  детектора, замен, правки регистра и force-списка (флип `Ctrl+`` ` `` работает). Когда
  своих сведений нет (после клика, стрелок) — берётся символ перед кареткой из
  `SetSurroundingText`; когда нет и его — сомнение вызывает только Backspace. Без улик
  слово, как и раньше, считается новым.
- **Двухбуквенные «слова».** В `ru.words` 244 двухбуквенных записи (большей частью мусор
  корпуса: «ть», «дл», «чт»), в большом словаре ещё 418 — треть всех возможных пар букв.
  Поэтому переводилась половина всех двухбуквенных латинских токенов: `TV` → «ЕМ», `UK` →
  «ГЛ», `16 GB` → «16 ПИ», `10 km` → «10 ль». Теперь для двух букв — список, как для одной:
  переводится только то, что входит в первую тысячу частотного списка (не, мы, ты, вы, на, но,
  он, то, по, за, из, до, от, да, бы, же…). Было 330 переводимых пар из 676, стало 26.
  Остаются честно двусмысленные `vs`/`dj`/`kb` (мы/во/ли).
- **Знаки препинания после переведённого слова.** Разделитель клался в обе версии слова
  латинским символом: `ghbdtn/` → «привет/», а каждая русская запятая — `?`. Теперь он
  рендерится в раскладке своей версии (`separator_in`): «привет.», «как дела?», а флип
  возвращает ровно набранное.

**Клавиши.**

- **CapsLock и буквы на знаковых клавишах.** Кейсим `;` одинаков с CapsLock и без, а буква
  «ж» на той же клавише — нет. «ВАЖНО» выходило как «ВАжНО», а «ЭТО» — как «эТО», что есть
  сигнатура «залипший CapsLock», и правка регистра делала из него «Это». В буфере теперь два
  уровня Shift на клавишу (`alt_shift`).
- **Alt+Shift тапом работал только в порядке Alt→Shift:** Alt при зажатом Shift приходит как
  `Meta_L` (второй уровень клавиши в xkb) и отменял жест.
- **F-клавиши, Menu, Print, XF86-клавиши** уходили приложению, пока слово ещё в preedit (F5
  запускал файл без последнего слова). Теперь сначала коммит. `Shift+Tab` — такой же жёсткий
  разделитель, как Tab. `Super+буква` от клиента, который ставит только бит `Mod4`, больше не
  считается набором текста.
- **GTK-приложения и «нет выделения».** GTK-модуль IBus называет себя `gtk3-im:<программа>`
  (`gtk-im:`/`gtk4-im:`), а код сравнивал с голым `gtk-im` — совпадений не было никогда, и
  отчёт «cursor == anchor» считался авторитетным. Модуль же во всех версиях GTK шлёт настоящий
  anchor только для `GtkTextView`, а сам отчёт присылает на каждое событие клавиши — включая
  Ctrl самого жеста. Итог: в Firefox перевод выделения отвечал «нет выделения» всегда.

**Прочее.**

- Движок завершается, когда соединение с ibus-daemon закрылось (после падения демона
  оставался сиротой, `doctor` показывал два движка).
- Каталог конфига создаётся до установки наблюдателя — иначе hot-reload и пауза из трея не

- Окно настроек не перезаписывает `config.toml`, который не удалось прочитать;
  `puntu settings` больше не предлагает ненужный `ibus restart`.
- **Установка на другую машину без сети.** `install.sh`, запущенный из распакованного архива
  релиза (рядом с бинарниками), раньше их игнорировал и качал последний релиз с GitHub —

### Автокоррекция опечаток — реализовано (0.9.6, `fix_typos`, по умолчанию выключено)

Сделано по ограничителям, записанным здесь же раньше, с двумя отличиями от первоначального
замысла — оба продиктованы замером, а не вкусом.

- **Кандидаты строятся перебором, а не автоматом Левенштейна.** `detect/typo.rs` порождает
  все строки на расстоянии одного *механического промаха* и проверяет их по словарю. Это
  дёшево (сотни проверок на слово), не требует фичи `levenshtein`, и — главное — позволяет
  считать промахом не «любую правку», а то, что делает палец: перестановку соседних букв
  (расстояние 2 по Левенштейну!), задвоенную букву, пропущенную, соседнюю клавишу вместо
  нужной или вместе с ней. «ревью» → «ревю» таким промахом не является.
- **Исправлять только на частотное слово.** Неизвестность слова проверяется по всему
  (большой FST + списки пользователя), а кандидат обязан быть в частотном списке `ru.words`.
  Большой словарь на 1,5 млн форм — это в основном слова, которых никто не набирает, и
  нормальное слово, которого в нём нет («коммит», «токен»), почти всегда в одном «промахе» от
  какой-нибудь такой формы («комми», «токе»).

Замер (7 600 синтетических опечаток частотных слов и 236 настоящих слов длиной от 5 букв,
которых нет в словаре: IT-сленг, чатные формы, имена):

| правило | опечаток исправлено | неверных замен | «исправлено» настоящих слов |
|---|---|---|---|
| любой промах от 5 букв, любой кандидат из FST | 88 % | 0 | ~10 % |
| любой промах от 5 букв, частотный кандидат | 88 % | 0 | ~7 % |
| **свой порог длины на вид промаха** (перестановка/задвоение 5, пропуск 6, соседняя клавиша 7, лишняя соседняя 8) | **67 %** | **0** | **0 из 236** |

Последняя строка — замер уже собранного кода через `puntu stdin`; первые две — модель того же
алгоритма на Python, на которой подбирались пороги.

Единственность кандидата считается по **всем** видам промахов, а порог длины применяется
уже к единственному — иначе опечатка «чинится» не в то слово (0,5 % в замере).

Остальное: только русские слова и только при загруженном `russian.fst`; заглавная буква —
это имя, если слово не начинает предложение (`starts_sentence` по тексту перед кареткой);
не в терминале, не при `dry_run`, не для фрагмента слова. Исправленное слово держится в
preedit; флип теперь трёхпозиционный — исправлено → как набрано → другая раскладка
(`Held::spare`, `Held::flip`). Откат исправления кладёт слово в `learned.ru.txt`, и больше оно
не исправляется. Английский не трогается: `en.words` на 70 тысяч слов не знает слишком
многого, чтобы «неизвестное» значило «с опечаткой».

Что осталось за бортом сознательно: слова короче порога («хоршо», «оченб»), неоднозначные
(«которй» — «который»/«которой»/«которые»), орфография («какойто», «вообщем»).

# Исходный утверждённый план (для истории)

# Puntu — аналог Punto Switcher для Ubuntu (Wayland/GNOME)

> Рабочее название: **Puntu** (Punto + Ubuntu). Можно переименовать.

## Контекст

Нужен open-source аналог Яндекс Punto Switcher для Ubuntu: фоновая утилита, которая
следит за вводом и, когда слово явно набрано не в той раскладке (например `ghbdtn`
вместо `привет`), удаляет его, переключает раскладку и печатает заново правильно.
Плюс сопутствующие удобства: ручная конвертация по горячей клавише, отмена,
(позже) автозамена, исправление регистра, индикатор в трее и GUI.

**Окружение (проверено):** Ubuntu 26.04 LTS, сессия **Wayland**, GNOME. `/home/alfer/Projects` —
общий каталог для всех проектов пользователя, поэтому код живёт в **отдельной подпапке
`/home/alfer/Projects/puntu/`**. Rust-тулчейн ещё не установлен. Пользователь **не** входит в
группу `input`. Клавиатура = `/dev/input/event2` (`platform-i8042-serio-0-event-kbd`).

**Главное ограничение — Wayland.** Классический аналог (`xneur`) и большинство гайдов
используют API X11 (XRecord/XTest/xdotool) для глобального перехвата и ввода. **На Wayland
это не работает принципиально** (клиенту не даётся глобальный перехват клавиатуры).
Надёжный путь на будущее — тот же слой, что используют `keyd`, `evremap`, `kmonad`, —
работа на уровне ядра **evdev/uinput**, ниже дисплейного сервера. Это работает одинаково
на Wayland, X11 и в консоли:

- **Перехват:** читаем сырые события из `/dev/input/event*` и делаем `EVIOCGRAB` клавиатуры.
- **Трансляция** keycode+модификаторы → символ через **libxkbcommon** с учётом *активной* раскладки.
- **Переключение раскладки** в GNOME через `gsettings org.gnome.desktop.input-sources current`.
- **Ввод** исправлений через виртуальную клавиатуру **uinput**.

**Решения (согласованы с пользователем):** Rust · первая веха = *ядро автопереключения*
(systemd user service, конфиг TOML, управление через **CLI**; GUI — в M3 поверх того же
бэкенда) · Русский ↔ Английский.

## Принцип работы (исходная идея)

Ключевая идея Punto: *одни и те же физические клавиши* дают разные символы в разных
раскладках. (Реализация: см. раздел «Статус» выше — повтор keycode заменён вставкой из буфера.)

1. Перехват + прозрачный ре-эмит через uinput. *(отклонено → пассивное чтение)*
2. Анализ по словам: копим keycode, транслируем в текст активной раскладки.
3. Детекция: сравниваем строку в текущей раскладке против тех же keycode в другой.
4. Исправление: backspace → переключить раскладку → повторить keycode. *(отклонено → буфер+Ctrl+V)*
5. Стек отмены + обучение «не срабатывать».

## Алгоритм детекции
- Токенизатор: буквы продлевают слово; пробел/пунктуация закрывают.
- Два кандидата: `S_cur` (текущая раскладка) и `S_alt` (другая).
- Скоринг триграммами: срабатываем, когда другая раскладка уверенно лучше и текущая невалидна.
- Защита: пользовательский словарь (исключения ∪ learned), список команд + эвристики,
  список force (всегда конвертировать).

## Корректное поведение при редактировании
Доверенный контекст: автокоррекция только когда слово набрано подряд и курсор в его конце;
навигация/правка/клик помечают контекст недоверенным. *(Уточнено: новое слово после клика —
доверенное; см. «Статус».)*

## Пользовательские словари, команды, сленг и обучение
Списки: исключения (manual), авто-обученные (learned), исправления (force), команды (commands).
Хранение: `~/.config/puntu/*.txt`, hot-reload. Хоткеи «в исключения» / «исправить+в исправления».
CLI: `puntu dict list/add/rm/forget/clear-learned`.

## Права доступа и запуск (без root)
systemd user service; группа `input` (чтение клавиатуры); udev-правило + модуль `uinput`

## M5 — Миграция на IBus engine (фундаментальное решение race conditions)

### Проблема текущего подхода

М1-М4 используют **uinput-инжекцию keystrokes** для коррекции: backspace удаляет неверное
слово, clipboard+Ctrl+V вставляет правильное. Это даёт **неустранимые гонки** при быстром
вводе:

1. **Pre-grab type-ahead**: между detection separator и активацией keyboard grab проходит
   ~30-100мс (wait_key_release). За это время user'овские нажатия попадают compositor → app
   напрямую. Расширение backspace count + replay через uinput частично решает, но создаёт
   следующую гонку.
2. **Replay vs typing race**: после ungrab мы replay'им user keystrokes через uinput,
   параллельно user продолжает физически печатать → события приходят в app в неправильном
   порядке (`gпривет`, `fработаете`, `sвырработаете`).
3. **350мс debounce** (текущее решение) устраняет гонки ценой того что **коррекция
   срабатывает только при паузе**. При непрерывной печати — слова остаются в wrong-layout.

Wayland `zwp_input_method_v2` на GNOME **недоступен** для внешних клиентов — Mutter
зарезервировал его для IBus как единственный input-method framework. Поэтому правильный
архитектурный путь = **реализовать IBus engine**.

### Архитектура IBus engine

IBus engine — это DBus-сервис, который IBus регистрирует как один из движков ввода. User
выбирает его через GNOME Settings → Keyboard → Input Sources. Когда движок активен, **все
keystrokes пользователя в текущем фокусе проходят через нас перед попаданием в app**.

```
┌─────────┐  keystroke    ┌──────┐  ProcessKeyEvent  ┌──────────────┐
│  user   │ ───────────→ │ IBus │ ────────────────→  │ puntu-engine │
│ kbd     │              │ daemon│                    │   (Rust)     │
└─────────┘              └──────┘ ←────────────────  └──────────────┘
                          │       commit_text/forward
                          ▼
                        ┌──────┐
                        │ app  │
                        └──────┘
```

**Поток обработки слова:**
1. User нажимает `g`, `h`, `b`, `d`, `t`, `n` → IBus передаёт каждое в `ProcessKeyEvent`.
2. Мы **возвращаем true** (handled) для каждой буквы и копим их в внутреннем word buffer.
   App пока не видит ничего — символы наши.
3. User нажимает SPACE → детектор решает Convert.
4. Мы вызываем `commit_text("привет ")` — IBus вставляет текст в app атомарно. Никакого
   backspace, никакого clipboard, никакого race.
5. Если detector решил Leave — `forward_key_event` для каждого keystroke (передать в app
   как есть).

**Преимущества:**
- Мгновенная коррекция (нет debounce)
- Нет гонок (мы единственный писатель в app)
- Layout-independent (commit_text принимает Unicode-текст)
- Корректно работает с любым приложением (text fields, terminals, IDE)

**Сложности:**
- IBus engine для wrong-layout детекции — нетипичный use-case (обычно engines делают CJK
  composition). Возможны edge-cases с `forward_key_event` для пропущенных слов.
- Live preedit: пока user печатает слово, app ничего не видит. Хорошо это или плохо — нужно
  тестировать с реальными приложениями (curses-апп типа vim может не любить).
- Совместное существование с другими engines (например, ibus-typing-booster).

### Этапы реализации

**M5.1 — Каркас IBus engine**
- Добавить зависимости: `zbus = "4"`, `serde` для конфига (уже есть).
- Создать `src/ibus.rs` с DBus-сервисом, реализующим IBus engine interface (`org.freedesktop.IBus.Engine`).
- Component XML файл `data/puntu.xml` для регистрации в IBus.
- `install.sh` копирует `puntu.xml` в `~/.local/share/ibus/component/` + cmd для запуска
  `puntu --ibus` как service.
- Bin target `puntu-ibus` (новый, отдельный от uinput-демона).

**M5.2 — Базовая обработка keystrokes**
- ProcessKeyEvent → классификация через существующий `keymap::classify`.
- Word buffer — переиспользуем `buffer::WordBuffer`.
- На separator → detector.decide() → commit_text(alt) или forward_key_event(original).
- Backspace в word buffer → корректно update preedit.

**M5.3 — Preedit (визуализация набираемого слова)**
- Через `update_preedit_text` показывать пользователю что мы накапливаем буквы.
- На separator — committed text появляется в app, preedit очищается.
- Тестировать на gedit, firefox, gnome-terminal, vim.

**M5.4 — Hotkeys и manual triggers**
- Pause/Break → undo last commit. Для undo нужно знать что было committed; можно через
  `delete_surrounding_text` + commit оригинала.
- Convert selection (Ctrl+Shift) — через `surrounding_text` API получить текущее выделение,
  заменить.

**M5.5 — Coexistence с uinput-демоном**
- Сохранить uinput-демон как **fallback** для приложений где IBus не работает (например,
  legacy X11 apps без XIM).
- CLI флаг `puntu --mode={ibus,uinput,auto}`. По умолчанию `auto` — определить по
  `XDG_SESSION_TYPE`.
- Один shared core (buffer, detector, dict, config); только frontend разный.

**M5.6 — Distribution**
- `install.sh` определяет GNOME → ставит IBus engine. Не-GNOME (sway, hyprland) → uinput.
- Документация в README: «GNOME: пользуйтесь IBus engine, переключите в Settings…».

### Оценка
~3-7 дней разработки (по 4-6 часов), плюс ~2-3 дня тестирования с разными приложениями.
Главный риск: GNOME Mutter может не поддерживать `forward_key_event` так как мы ожидаем,
либо preedit может конфликтовать с native input. Мини-PoC (M5.1+M5.2 за 1 день) даст
понимание.

### Известные альтернативы (отвергнуты)
- **zwp_input_method_v2 напрямую через wayland**: на GNOME недоступно для не-IBus клиентов.
- **GNOME Shell extension через mutter API**: язык JS, не Rust; работает только в GNOME.
- **Полностью отказаться от auto-correct**: лишает проект главной фичи (Punto-style).
